1. Summary for the committee

The Universal Medical ML/NeuralNet Predictor is a web application for developing and evaluating clinical prediction models (for example, predicting response to a neurosurgical procedure from routinely collected variables). It offers logistic regression, Random Forest, gradient-boosted trees, k-nearest neighbours, naive Bayes, neural networks, an ensemble and Cox survival models, with the validation and reporting methods expected in prediction-model research.

Where patient data are processedOnly in the researcher's own web browser, on the researcher's own computer. The application has no server component and no database.
Is any patient data transmitted?No. The page is technically prevented from sending data anywhere other than its own address (section 3.2), and this was confirmed by monitoring the network traffic of the published site during a full analysis.
Can it run without internet access?Yes. The complete application can be downloaded and opened from the computer's disk with the network disconnected (section 3.3).
What does it store on the computer?Only the researcher's analysis settings (choices and column names), never patient values (section 3.4). Files are written only when the researcher chooses to export them.
How has accuracy been checked?66 automated comparisons against established statistical software (SciPy, scikit-learn, statsmodels, scikit-survival, pmsampsize), an equivalence benchmark against scikit-learn, PyTorch and imbalanced-learn, two open-source audit tools (Fairlearn, Deepchecks) and a suite of end-to-end and browser tests that run automatically on every change (section 6).
Intended usersClinicians and medical researchers (initially neurosurgeons) developing or validating prediction models for research.

2. Intended use and regulatory status

Intended use

  • Exploring de-identified or pseudonymised research datasets and comparing prediction methods.
  • Developing candidate prediction models, with internal validation (train/test split, cross-validation or bootstrap).
  • Validating a frozen model on a separate cohort, including a model received from another centre, without sharing patient data between centres.
  • Producing results and documentation for research reports, aligned with the TRIPOD+AI reporting guideline.
  • Teaching the principles of supervised machine learning and prediction-model evaluation.

Not intended for

  • Diagnosis, treatment decisions or any decision about an individual patient's care.
  • Use as a clinical decision-support system in routine practice.
  • Processing identifiable patient data where a de-identified dataset would serve the research purpose.

Regulatory position

The software is not CE- or UKCA-marked and is not registered as a medical device. Software used to guide individual patient care may be regulated as a medical device (for example under UK MDR 2002 / MHRA guidance on software as a medical device, or EU MDR 2017/745). The application displays a research-use notice on its prediction screens, and every exported report, model file and checklist carries the statement “Investigational research and education use only. Not a certified medical device; not validated for individual clinical decisions.”

3. How patient data are handled

3.1 Data flow

1. OpenThe researcher selects a CSV file on their own computer.
2. ReadThe browser reads it into the page's working memory. No copy is uploaded.
3. AnalyseAll calculations run in the browser, partly in a background thread of the same page.
4. ViewResults appear on screen.
5. Export (optional)Only when the researcher clicks an export button is a file saved, to their own computer.

Closing or reloading the page discards the data from memory.

3.2 Technical safeguards against data leaving the computer

  • No server and no data upload. The website delivers only the application's own files (program code, stylesheet and simulated example datasets). It has no account system, database or upload function.
  • Content Security Policy. The page declares a browser security policy that only allows it to contact its own address (connect-src 'self'), forbids form submissions to other sites (form-action 'none'), blocks plug-ins (object-src 'none') and allows scripts only from its own files or by cryptographic hash. The browser enforces this policy, so even a programming error could not send data to another server.
  • No third-party components at run time. No analytics, advertising, tracking, fonts or scripts are loaded from other organisations. The libraries the application uses (TensorFlow.js and Chart.js) are served from the application's own files.
  • Untrusted files are checked. Model and settings files loaded into the application are treated as untrusted: they are read as plain data only (a file cannot add program code), checked against the expected structure, and a model must predict a test patient correctly before anything is installed.
  • Clear session. A “Clear session and patient data” button discards every loaded dataset, result, trained model and cached imputation from the page. Closing the browser tab has the same effect.
  • Verified on the published site. In October 2026, every network request made by the published application during a complete analysis (loading data, training models, making predictions) was recorded: all went to the application's own address, all were downloads of its own files and example data, and none sent data out. The same check is repeated automatically by a browser test on every change to the software.

3.3 Offline use (recommended where governance requires it)

The whole application can be downloaded from the source repository and opened directly from the computer's disk (by opening index.html), with the network switched off. It then works without any internet connection. Institutions that prefer can therefore keep the software, like the data, entirely within their own managed computers.

3.5 Researcher and institution responsibilities

Keeping data in the browser supports data-protection-compliant research, but software alone cannot make a study compliant. Researchers should:

  • use de-identified or pseudonymised data, removing names, hospital numbers, dates of birth and free text that are not needed;
  • run the application on an institution-managed, encrypted computer, offline if local policy requires;
  • store any exported file that contains patient-level values (section 3.4) under the same rules as the source data, and share model files of those types only where data-sharing approvals permit;
  • complete the data-protection assessment (for example a DPIA) and confirm the lawful basis for processing required by their institution.

5. Safeguards against misleading results

Prediction models are easily over-optimistic. The application contains specific protections, each of which is tested:

  • No information leakage. Missing-value filling, encoding, scaling, class balancing, feature selection, tuning and recalibration are fitted on training patients only and refitted inside every cross-validation fold and bootstrap resample. On data with no true signal, the corrected performance estimates are about AUC 0.5, as they should be.
  • Patients with several records. Splits, cross-validation and bootstrap resampling can keep each patient's records together, so a patient is never in both the training and the test set.
  • Optimism and uncertainty. Results carry 95% confidence intervals; small test sets, few events per predictor and small subgroups are flagged; training (apparent) performance is never presented as evidence of predictive validity.
  • Probabilities. Calibration is reported alongside discrimination; vote shares are labelled as such; recalibration is offered and fitted without the test patients.
  • Inputs. Values outside the range of the training patients, unknown categories and blank values are flagged on every prediction.
  • Reproducibility. All random processes are seeded; the seed and software version are recorded in every report and model file.

What this evidence does and does not show

These checks show that the software calculates the methods it offers correctly and guards against common methodological errors. They do not show that any particular prediction model is accurate for patients: that depends on the data, the outcome definition and the study design, and must be established by the research itself, ideally by validation in an independent cohort (which the application supports). The verification was carried out by the developer, using AI-assisted programming tools, and has not been certified by an external body; the published tests and reports allow independent repetition. Demonstration datasets supplied with the application are either simulated or public (Breast Cancer Wisconsin, UCI) and contain no real patients' data.

8. Reporting and reproducibility

  • The application pre-fills a reporting checklist aligned with TRIPOD+AI (Collins et al., BMJ 2024) and drafts a methods paragraph; researchers complete the items that depend on their study.
  • Risk of bias and applicability of resulting models can be assessed with PROBAST+AI.
  • Every report and model file records the software version, the random seeds and the settings used; saved settings files allow an analysis to be repeated exactly.
  • The source code, its complete change history and all verification reports are available at github.com/Rasan17/ml.

9. Suggested wording for an ethics application

Researchers may adapt the following paragraph:

Prediction models will be developed using the Universal Medical ML/NeuralNet Predictor (version 2.2, build 2026.10.18; Dr G Narenthiran), a browser-based research application in which all data processing takes place locally on the researcher's computer. No patient data are transmitted to any server; the application has no server-side component and its security policy prevents network transmission, which has been verified on the published version. The application [will be run offline from a local copy on an institution-managed encrypted computer]. Only [de-identified / pseudonymised] data will be analysed. The software's statistical calculations have been verified against established statistical software (SciPy, scikit-learn, statsmodels, scikit-survival) and open-source audit tools (Fairlearn, Deepchecks); verification reports are publicly available. The software is research software, not a medical device, and no results will be used for decisions about individual patients' care. Model development and reporting will follow TRIPOD+AI.
